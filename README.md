# RSSD for Obsidian (stage 1)

This repository is checked out at `obsidian/` inside an
[RSSD](https://github.com/scholay-rssd/rssd) checkout and imports its shared
`contracts/`. Run the commands below from that directory.

## Read articles online (no download)

Install the plugin into any vault and open it. A welcome window offers **Log in to RSSD**: the browser opens, you sign in and approve the device, and the **RSSD reader** tab opens with the site's published articles. Click an article to read it rendered, with its images; nothing is written into the vault. Switch site (when the device is approved for several), language and *Include unpublished drafts* at the top. Reopen it later from the book ribbon icon or the *Read site articles online* command.

The Center address defaults to `https://post.linkc.cloud`; build with `RSSD_DEFAULT_ORIGIN=https://… npm run build` for another Center. A login from the welcome window does not choose a sync space, so automatic sync stays off until someone picks a **Sync space** in Settings for editing.

## Edit as drafts

Open one RSSD Center space as a vault of drafts, see each work's sync state, and save edits back as **private drafts**. Nothing here publishes.

## Use

1. Create an empty vault **outside the git repo**, one vault per space (a space is a site).
2. Build and install:
   ```sh
   npm install
   npm run build
   node install.mjs /path/to/vault
   ```
   After this first install, new versions arrive by themselves (see *Plugin updates*).

   **For a new writer:** `npm run starter` (`node release.mjs starter [--out <folder>]`) packages the Center's current signed release as `rssd-starter-vault-<version>.zip`: an empty vault named `RSSD` with the plugin installed and enabled, and a note `开始使用.md` with the steps. It checks the release's signature and file hashes the way a vault does, needs no key, and holds no token or settings, so it can be sent to anyone. They unzip it, open the folder in Obsidian, trust the plugin and add their device token (below); the plugin updates itself from then on.
3. In Obsidian enable the plugin, open Settings → RSSD, enter the Center address and run **Log in to the RSSD Center**. Approve the device and its spaces in your browser.

   **Without the browser:** someone with the Center's owner account creates a device connection under the Center's 设置 → 设备连接, choosing its spaces, and copies its credential. In Obsidian, add that credential under Settings → Keychain (any name), then choose it under Settings → RSSD → **Device token from the Keychain**. The plugin checks it with the Center and keeps only the secret's name; a vault with no space yet takes the token's only space. This suits a part-time writer who should see one or two spaces: give each person their own connection, and revoke it in the Center when they leave. A later browser login replaces the Keychain choice.
4. Run **Update works from the Center**. Chinese works appear in `Works/<id>.md`, English works in `Works/en/<id>.md`, and images in `article-media/`.
5. Automatic sync is on by default. While Obsidian and the vault are open, it checks for remote changes periodically and saves edits to linked works as private drafts after a short delay. It discovers offline edits after reopening. A save that is refused is reported once, and that work waits until you edit it again; a lost connection is retried by itself. A private record waiting for a work in `.rssd/private-additions/` goes with that work's next save, even when its note is unchanged. Use Settings → RSSD → **Automatic sync** to turn it off. The manual update and save commands remain available.
6. Active spaces save to Center private drafts. When the Center advertises staged-draft support, a staged space saves an independent private migration draft based on its imported snapshot; the original site still owns publication, and later legacy changes can require reconciliation. Neither kind of save publishes. Mobile is read-only.

Commands: *Log in*, *Update works*, *Save this work*, *Check sync state of all works*.

**Update** brings the Center's latest versions down into the vault, and **Save** sends edits up as private drafts. Internally an update is still a *pull*: the command id and the `pull` action for command links are unchanged, so existing hotkeys and links keep working.

## A key decides the vault

Install the plugin (or open a starter vault) and the **连接 RSSD** window asks for a key. Keys are made by the Center's owner at `/rssd?tab=workers` (设备连接), each with the sites it covers and, when ticked, the RSSD Center itself. The key decides what the vault is: one site and no Center gives a vault of that site with `Works/` at the root; several sites, or the Center, give each site a folder of its own. Every site in the key is downloaded at once, with progress in the Works list. The owner can also use **用浏览器登录**, which approves this device in the browser and works the same way.

Settings → RSSD shows the key first: the sites it covers, or a field to paste one. Everything else is under **高级设置**. A later key must still cover the sites the vault holds; otherwise it is refused and nothing changes. When the Center answers that the key was revoked, the plugin says so once, stops syncing and asks for a new key; local works and unsaved edits stay and are saved after the new key is in. Revoking cannot remove what a vault already downloaded.

## Work cards and the topics list (2026-11-20)

Each work card is one row of icons under its title. The first icon says where the work stands: local trouble first (conflict, saving, edited, not downloaded), otherwise the website (green globe published, an upload cloud when the draft is newer than the website, a red cross when a publication is stuck, a send icon while it runs, a dashed circle when never published). Then the date with its year, length, pictures, references and the other language's edition, each only when there is one, and orange or red icons for open checks and a missing author or category. A second line always names the agent and model that wrote it (or 未记录) and the machine that first saved it. Hover any icon for its meaning. The open work's card has one icon per RSSD tab (article, cards, outline, details) to switch the editor to it, the tab in front highlighted, and a Save icon when the work has edits.

A vault with topics (a topic pool, or a key that includes RSSD Center) has a 选题 (light bulb) ribbon icon and the command *Show the topics list*: every topic note in one list, searchable, narrowed by 全部 / 待认领 / 写作中 / 受阻, highest priority first, each card showing its state, priority, type, due or last update, and a pencil when the note has edits the Center does not have. The refresh button updates the topics; clicking a card opens its note, where it is edited and saved as before.

## A key that includes RSSD Center

A key made with **RSSD Center** ticked (Center → 设置 → 执行设备 → 连接设备) gives each site's folder its topics too: `<site>/Topics/<section>/<title>.md`, with the same rules as the topic pool vault (edit a topic nobody has claimed, a new note in a section folder becomes a topic, withdraw, replace with the Center's version; the commands act on the topic in front). **Update** brings works, then topics, then each site's newest website publications: a work whose publication is stuck shows a red **发布失败** mark with the Center's reason, one still going a quiet **发布中**. Publications are matched to works by their Center work ID (recorded from now on as works are updated) or, until then, by a title only one work has.

## Several spaces in one vault

A new vault holds every space its login is approved for, each in a folder named after its site (for example `pet.piggytuck.com/`). Inside a space folder everything is laid out as in a vault of one space: `Works/`, `Works/en/`, `article-media/`, `.rssd/private-additions/`, `card-styles/`, `Card Samples/` and `Exports/cards/`. A part-time writer whose token is approved for one or two spaces sees only those. Settings → RSSD → **Spaces** lists the approved spaces; untick one to stop updating and saving it (its folder stays). Which spaces are approved is decided by the Center, not here.

**Update** goes through the ticked spaces one after another. The Works list shows which space and how many works so far, and each note appears in the list as soon as it is written. A space that fails is reported and the rest still update. The Works list gets a **Space** filter when it holds more than one space, and each section label belongs to its space.

A vault that already holds one space's works (or chose a sync space, or is a topic pool) keeps its layout, with `Works/` at the root. Logging in from the welcome window, for reading only, puts no space in the vault until one is ticked in Settings. See `docs/obsidian-center-vault.md` in RSSD for the plan: adopting existing single-space vaults and the topic pool come next.

## Topic pool

A vault can instead show the topics waiting to be written, across every space the device is approved for. Use a separate, empty vault for it.

1. Install the plugin, log in, and under Settings → RSSD set **Vault purpose** to **Topic pool**. Do not choose a sync space.
2. Run **Update the topic pool**. Each open write demand becomes one note under `Topics/<space>/<section>/`, named after its title. The vault then follows the Center on its own, shortly after opening and hourly.
3. A note's `title`, `priority`, `type` (`article` or `note`), `topic-key` and `due` properties, and its text (the brief), can be edited while nobody has claimed the topic. **Save this topic to the Center** sends only what changed.
4. A new note with a `title` property and a brief, placed in a section folder, becomes a topic with the same command. The Center refuses a topic that repeats a work or an open topic of that section and says which.
5. **Withdraw this topic** cancels a topic nobody has claimed and removes its note. **Replace this topic with the Center's version** discards a note's unsaved edits.

A topic is identified by its `rssd-demand` property, so its note may be renamed. Properties starting with `rssd-` are the Center's and are rewritten on update. An update never overwrites a note with unsaved edits; when the Center's side changed too, the note is reported and left as written. Finished topics keep their note with the work's ID in `rssd-work`; the first update of a space brings only open topics. Mobile can update but not save.

This needs a Center with the demand pool endpoints (list filters, `updatedSince`, device withdrawal). An older Center still lists topics, but returns the whole queue on every update and refuses a withdrawal.
## Annotating a work

The review sidebar has a fourth tab, **标注**. For the open work it asks the Center which questions apply to the published revision readers see, and shows them: 1 to 5 scales, single choices and yes or no. Answers are kept on this device until submitted, so switching works or tabs loses nothing. Submitting adds a record at the Center and never changes the work. Submitting again adds a newer record, and the newest counts.

Only a published revision of an article or a note can be annotated. When the note in the vault is a newer draft than what is published, the tab says which revision the answers are about. This needs a Center with the annotation endpoints; an older Center is reported as not supporting annotation.

## Rules (from the RSSD business spec)

- The Center is the source of truth. Do not run Obsidian Sync, iCloud or Git on this vault.
- A note is identified by its `rssd-id` property, never by its file name. Do not edit the identity properties (`rssd-id`, `rssd-section`, `rssd-locale`, `rssd-kind`, `rssd-version`, `rssd-published-version`, `rssd-adapted-from`, `rssd-adapted-revision`). The work's type and tags (`rssd-type`, `rssd-tags`) are edited in **Details**.
- An update never overwrites a note with local changes; a conflict is reported and the note is left as written.
- The Center sends bounded batches when supported; the plugin falls back to limited individual reads. Interrupted updates retain completed work and report failures for retry.
- A save carries the exact base version and is refused if the Center moved. The Center must explicitly confirm it preserves existing attachments and editorial metadata. It never publishes.
- A save whose answer was lost keeps its request key and is recovered by that key, never resent.
- Structured records (`year`, `history`, `openSource`) require a Center that explicitly supports safe private drafts. Only the title and the prose inside their existing named sections are editable; the first Markdown H1 must match the title. Other properties, section names and source fields must remain unchanged. Invalid edits stay local and are reported.
- Referenced images are detected by their bytes and uploaded by content hash. Supported syntax is a relative Markdown path under `article-media/` or an explicit `![[article-media/name.png|alt]]` embed. Ambiguous `![[image.png]]`, files in other directories and unreferenced hidden-attachment replacement cannot be safely synchronized. A work may reference at most 12 PNG, JPEG or WebP images. A save sends at most 2 MiB of picture bytes: pictures the Center already keeps with the work go by their path alone (on a Center whose work details say `reusesStoredMediaOnSave`), so only new or changed pictures count. Over the limit, the save is refused before anything is sent and names each picture with its size.
- New unlinked notes, local renames and local deletions do not create, rename or delete Center works. Moved or missing linked notes are reported and are not silently recreated. Return the original note to its linked path to resume syncing.

## Work types, tags and notes

Every site takes long articles (长文) and short picture-led notes (笔记); which types a section takes, and which comes first as its default, is set per section in RSSD's `contracts/site-sections.mjs` (bundled when the plugin is built, read with `sectionWorkPolicy` from `contracts/work-types.mjs`). A section that declares nothing takes long articles only.

- **Type.** Details has a Type row that offers only the types the work's section takes. A note without `rssd-type` is its section's default and says so. Choosing a type writes `rssd-type` into the note, and the next save sends it. A calendar entry, historical event or resource keeps the type its record kind fixes. A work's type may change after it is published; the website follows with the next revision. In the Works list a note carries 笔记 after its section.
- **Tags.** The Tags row takes the work's own #tags, separated by commas: at most 10, each up to 40 characters, a leading `#` is dropped and each tag is kept once. They are written to `rssd-tags`; an emptied list stays as `rssd-tags: []`, so the save clears them at the Center. The site shows them after the tags its organization file binds to the work.
- **Rewritten from.** A note made from a long article carries `rssd-adapted-from` (a link to the article's note, `"[[Works/<id>]]"`) and `rssd-adapted-revision` (the article revision it was written from). Details links back to the article and says when the article has a newer revision; an article's Details lists the notes made from it.
- **Rewrite as note.** On the Chinese edition of a saved long article in a section that takes notes, **Rewrite as note** (in Details, or the command *Rewrite this article as a note*) makes a new note work in the same space and section: `Works/<article id>-note.md` (then `-note-2` and so on), starting from the article's title, summary, standalone pictures and tags, linked to the article's current revision, and saved at once as a private draft. Nothing is published, and the article is not changed. The note is a work of its own, never the article's card page. Save the article first: the note must name a revision the Center has. A migrating space cannot make new works.
- **Which Center gets them.** The type, source link and tags are sent only to a Center whose `/site` lists `work-types-v1`, and only when they differ from the Center's own values: omitted, the Center keeps what it has. To any other Center nothing new is sent, and a note that asks for a note type, tags or a source link is kept local with a message instead of losing them. A migration (staged) draft keeps the type, source link and tags of its edition; a change is refused before anything is sent. A note without these properties keeps the sync fingerprint it always had, so updating the plugin marks no work as edited.

## Interrupted updates and saves

- An update can take time, especially when articles include images. A batch can wait up to 300 seconds for the same request; after that the current update stops rather than duplicating a request that Obsidian cannot cancel. Wait for the connection to recover before running **Update works from the Center** again. Already confirmed articles and their baselines are retained; the next update checks them and resumes the remaining work.
- A finished update can still report skipped local edits, conflicts, unresolved saves or failures. Skipped local edits are preserved; conflicts need review before another save. The latest operation's private `.obsidian/plugins/rssd/last-run.json` includes its state, progress and any recorded errors. Keep this file and the plugin's settings private.
- If the answer to a save is lost, leave the note and plugin settings in place. Run the save command again on that note: the plugin checks the original request's Center receipt instead of submitting a second draft. An unresolved receipt is not proof that the save failed or succeeded.
- Sync records are kept in the plugin settings (`data.json`) together with a small `baselines.journal` beside it. The journal holds the newest changes until they are folded into the settings file, so keep, back up and restore the two files together; the journal is absent when there is nothing to fold in.
- If a save succeeds but warns that its local version label could not be refreshed, the Center draft was saved. A later update attempts a safe refresh of the `rssd-version` label while preserving note edits; do not send another save merely to repair the label. If the warning persists, inspect the note's identity properties and local changes.

## Formatted article and layout preview

With a work open, run **Copy this work as a formatted article** (also in the status-bar menu), then paste into a rich-text editor. The output is tuned for the WeChat official-account editor but is not tied to it. The styling comes from the website's own export engine (`web/engine/browser-export/wechat-clipboard.mjs` in RSSD). Images from `article-media/` travel inside the copied content as JPEG or PNG. The title is not part of the body: put it in the editor's title field. This only fills the clipboard; nothing is sent to the Center or to any platform.

The four RSSD tabs open in the note's own tab bar, next to the note, where each has the full width: from the open work's card in the Works list (each button has its tab's icon), from the commands, or from the note's menu. Each tab is named for what it shows and the work, for example "Article · 生存分析如何读懂未完的随访". A second one opens next to the first, and a tab you drag elsewhere reopens there. The right sidebar is left to Obsidian. **Article** and **Cards** are the outputs. Each follows the work you have open and refreshes after edits, and has one row of controls: first **Default**, the site's own style, then the general themes as numbered squares in the section's colour (hover a number for its name), then refresh and copy or save. On desktop that row sits in Obsidian's status bar while the tab is in front, so the preview has the whole tab; on mobile, which has no status bar, it stays at the top of the tab. The article preview is a phone-width column, 375px with WeChat's 16px side margins, as a 公众号 reader sees it on a phone; it is centred on white with no visible edge, and wide tables or code scroll inside it. **Outline** lists the work's headings and brings the note to the front at the one you choose; **Details** edits the readers' fields (title, summary, date, author, category) with a count against each output's limit, lists what still needs filling, and shows the read-only fields that link the note to its Center work. A tab behind another is only built when you show it. Because the details have this place, the properties block at the top of each note is hidden (Settings → RSSD → *Properties in the article* shows it again). A vault arranged by an earlier version has its RSSD tabs closed once where that version put them (the right sidebar, or a pane of their own beside the note); they open next to the note from then on. Obsidian's own right-sidebar tabs that an earlier version closed can be reopened from the command palette. The copied article has no outer card, border or width of its own: it fills the editor's column, long links and code wrap, and pictures never exceed the column or their own size.

Each work takes the colours, fonts and heading mark of its space and section from the website's templates (`web/themes/export/templates/` in RSSD), which are bundled when the plugin is built; a work in a section without a template uses the default look. On top of that, each site has its own design (`src/wechat-designs.mjs`): how a chapter opens, how the site signs its name above and below the article (name and slogan come from `sites/profiles.json`), and how bold terms and inline code read. Second-level headings are the chapters; a heading such as 参考文献 stays quiet and unnumbered.

The **Cards** tab lays the same work out as picture cards: 3:4 PNG images of 1080×1440, with the site name and section across the top, the site's address and the card number at the bottom, and the section's own page layout and colours. Layout and drawing are the website's page engine (`web/engine/browser-export/pagination.mjs` and `raster.mjs`), which refuses to produce a set that lost any text or picture. **Save cards** (or the command **Save this work as cards**) writes a package into the vault at `Exports/cards/<note name>/`, or `Exports/cards/en/<note name>/` for an English edition: the numbered pictures, `caption.txt` (title and summary) and `manifest.json`, whose language and source version are that edition's own. Each language edition has its own card set, made from its own revision, so English cards never replace Chinese ones. Saving again replaces that folder's cards. Nothing is sent anywhere. Only long articles get cards: a note's pictures are its content, so the Cards tab and **Save cards** refuse a note. Cards use the fonts on the computer that draws them, and a picture hosted on another site is left out and listed in the manifest.

**Looking at the cards.** The tab shows the set one of two ways, chosen in the middle of its toolbar: one card, with a rail of thumbnails beside it, or all cards as tiles. One card is fitted whole to the pane and never drawn larger than half size (540px wide), which is exact on a 2x screen and close to how the card reads on a phone. Clicking the card switches between that and **手机**, the 375px it has on a phone, the same width the article preview uses; use it to judge whether small text and formulas really read. The minus and plus buttons, or Ctrl-scroll, step through fit, phone size, 50% and 100%, with fit taking its place by how large it is in the pane, so zooming in never shrinks the card. All cards start as small tiles for seeing the whole set and step up to the same reading sizes; clicking a tile opens that card. The size shown between the buttons returns to the default when clicked. The left and right arrow keys move between cards in both.

**The cover.** Whichever way the cards are made, the first card carries a picture. The algorithm layout takes the work's first picture, with its caption, and sets it directly under the title, a little lower than a body picture so the title, the picture and the start of the text share the card; a work that already opens with its picture keeps its order, and a formula is never the cover. This is the same choice the cover rule in RSSD's `contracts/output-package.mjs` makes: the cover given, else the article's first image, else the site's default cover. Cards made outside the plug-in and shown from `Card Samples/` (智能排版 and 模型生图) are shown as given, so whoever makes them follows the same rule: the first card shows the work's own first picture, or a picture made for it, never text alone. A work with no picture at all still gets a text cover here, because the site's default cover is a file on the website, not in the vault.

**Captions, indent and notes on the algorithm layout.** A paragraph directly under a picture or table that starts 图：, 表：, Figure: or Table: is its caption: small, muted and centred. Chinese body paragraphs get a two-character first-line indent. Citation numbers such as [1] become shoulder marks, and everything under the closing 参考文献 heading, at any heading level or as a bold line, is set smaller.

**AI card styles.** An agent can give a column its own card design by writing one stylesheet, `card-styles/<column>.css` in the vault (for example `card-styles/methods.css`). The agent writes only CSS: Obsidian still lays the work out and draws the cards, measuring with that stylesheet, so larger type simply gives more cards, and the set is still refused if any text or picture would be lost. The Cards tab then offers **AI** after the numbered styles for every work of that column, and redraws on its own when the file is saved. The command **Copy the AI card style brief for this column** copies what the agent needs: the file to write, every element on a card (`.rssd-page`, its header and footer, `.rssd-body` with the title area, headings, paragraphs, quotes, code, tables, pictures and formulas), the column's layout and colours, and the rules. The plug-in refuses a stylesheet that would load or run anything (at-rules, `url()`, escapes, HTML), uses `!important` or nesting, addresses anything outside `.rssd-page`, resizes or moves the card itself, or adds words (`content` may only be empty, for lines and marks). After layout it also checks every piece of text on every card, header and footer included, and refuses the cards if the style hid it, faded it below 60%, set it below 12px, made it transparent or pushed it off the card (`src/card-stylesheet.mjs`). Nothing is fetched and no AI is called by the plug-in: the agent that writes the file is whichever one works in the vault.

Formulas are written the way the website writes them: `$…$`, `$$…$$`, `\(…\)` or `\[…\]`. Obsidian's own editor only draws the dollar forms, but both views draw every form with the website's KaTeX version (bundled, with its fonts) and carry each formula as a picture: a sharp PNG in the copied article, a vector picture on a card. An inline formula sits on the text baseline; a display formula is centred on its own line. In the article's plain text a formula is its LaTeX source. A formula delimiter left unclosed leaves the formulas as text and is listed in the manifest.

Every output also has a package manifest, defined in RSSD's `contracts/output-package.mjs`: the format, article, language, site, section and style, the source version and a hash of the source it was made from, and the fields the platform asks for besides the body (for WeChat: title, a digest of at most 120 characters, author and cover). The layout preview shows how many items the manifest flags, such as a missing author or cover or a shortened digest; hover the text to read them. The manifest is built in memory for now; nothing is written to the vault.

## Plugin updates

Once a vault has a released version, it keeps its RSSD plugin current by itself. A few minutes after Obsidian opens, and then every three hours, it asks the Center for the latest release (`/api/rssd/public/v1/obsidian-plugin/latest`). It installs a newer release only when it is signed with the RSSD release key and every file matches its signed hash. The public half of the key, `release-key.pub`, is compiled into every build. The files that ran before are kept in the plugin folder's `previous/`, and the plugin reloads once no sync is running. Settings → RSSD → **Plugin updates** turns this off for a vault or checks right away. *Roll back the RSSD plugin to the previous version* puts the previous files back, and that release is then skipped until a newer one appears.

To release, merge to `main`, then run `npm run release` (`node release.mjs publish`) from any checkout of this repo on the Mac that holds the release key. It:

- clones rssd-obsidian `main`, and rssd `main` with the themes and sites it pins, fresh from GitHub;
- installs dependencies from the lockfile, runs the tests (a failure stops the release) and builds;
- numbers the release with `manifest.json`'s major.minor and a patch one past both the Center's latest and the last release recorded in `~/.rssd/obsidian-plugin-releases.json`;
- signs it with the private key in `~/.rssd/obsidian-plugin-release.pem`;
- uploads it to the Center over SSH (`--server`, default `scholay-postiz`). The Center refuses a release that isn't signed with the key it pinned at the first publish, or that lowers or reuses a version;
- checks what vaults will receive.

Nothing local or unmerged goes into a release. `--dry-run --out <folder>` builds and signs with a throwaway key that no vault trusts, and uploads nothing (`--plugin-ref <branch>` builds another branch for that). `node release.mjs key` created the key once. Keep the private key backed up. A new key (`key --rotate`) means one more manual install in every vault. The Center also has to forget the old key: remove `/opt/postiz/data/config/rssd-obsidian-plugin/release-key.pub` on the server before the next release pins the new one.

Release builds carry their version and update themselves. A development build (`npm run build`) installs a signed release only when you check from Settings → RSSD or the command.

## Develop

`npm test` runs the plugin's rules against an in-memory vault and a stub Center, with a stand-in for Obsidian's API, so Obsidian itself is not needed. Three files import Obsidian: `src/main.js`, `src/review-sidebar.mjs` and `src/annotation-tab.mjs`. Every other module is handed the vault, the network and whatever else it needs from Obsidian, so the same code runs in the tests, on desktop and on mobile. The sync rules are in `src/sync-model.mjs`, `src/sync-engine.mjs`, `src/center-client.mjs` and `src/device-login.mjs`. Sync-state logic is shared with the rest of RSSD through `contracts/sync-state.mjs`.

## Works panel and command links

The **Works** tab in the left sidebar (or the command **Show the Works list**) shows readable titles and current sync states. Space selection lists authorized spaces; after downloading works the vault is bound to that space. A staged private draft is a separate migration branch and does not activate its site. Mobile cannot save private drafts.

Command links are off by default and can be enabled in RSSD settings for an operator-controlled vault. Example:

```
obsidian://rssd?vault=metho&do=status&requestId=status-001
```

Supported actions: `login`, `pull`, `status`, `spaces`, `save`. Save also requires an exact `path=Works/<id>.md` or `path=Works/en/<id>.md` (URL-encode the path). Each accepted command writes `.obsidian/plugins/rssd/runs/<requestId>.json`; `last-run.json` is a convenience copy. Reusing an ID returns the previous record, including an interrupted `running` record; it never repeats the action. Use a new command ID for an intentional retry. A pending draft save is still reconciled by its original **Center** request key. Keep these receipts private; no token is written into them.

Buttons, commands, panel refresh and command links share one operation gate. A busy vault refuses another operation rather than queuing a potentially stale save. Failed login preserves the server error and closes its modal; an old token does not turn that failure into a success.

## Reading a work

A work note opened in reading mode is a proofreading view, not a copy of the website's look (that is the Article tab): a page-width column (680px) with Chinese typography and a line height of 1.8, headings in clear steps, citation numbers kept quiet, the 参考文献 / References list set apart under a rule, a caption under each picture from its alt text ("No caption" in red when there is none), the site's brand line marked "Brand", and under the title a context line with the section, date and writer (agent · model, and the machine once the Center names it). Editing mode and every other note keep the vault's theme. Nothing here changes the note.

### Internal notes

The Center keeps a private record with each edition: internal notes (补充说明, 写作说明, 配图说明, 核对与待办, 其他备注), notes pinned to a paragraph, heading or picture, and every run of every agent. Obsidian shows it read only and never writes it into the note or any output. **Details** lists the internal notes, with 核对与待办 first, and the runs (time, action, agent · model). In reading mode a paragraph or picture with a pinned note carries a small mark that opens the note in place. A card shows a checklist icon while 核对与待办 has items; hovering it shows them. The record is read once per version of the work.

## Works list

The left sidebar's **Works** tab lists every work of the space, newest first by the work's own date, each with its section as a coloured label before the title. Search covers titles and summaries. The filter button beside it opens a floating filter panel, and every change applies at once: **Show** All, **Edited** (changed since the last sync with the Center) or **To check** (still missing an author or category); **Language**, 中文 or English, when the space has English editions; **Section**, **Agent**, **Model** and **Machine**, where several can be ticked and any of them matches; and **Date**, a from–to range with quick choices for the last 7 or 30 days and this month. The count beside each option is how many works it would list with the other choices kept. The button shows how many filters are in force, each filter shows as a chip under the search box that removes it, and the filter is remembered on this device. Within a filter any chosen value matches; across filters all must (`src/works-filter.mjs`). Each work is a card. What needs attention leads the card's row of facts as coloured icons, with the full explanation on hover: edited (pencil), saving, a conflict (warning), a note not yet updated from the Center (broken link), open checks in 核对与待办 (checklist; hovering shows the open items themselves) and a missing author or category; a work with nothing to attend to has none. What the website shows is not on the card. The rest of the row describes the work: its date, length (Chinese characters plus Latin words, or words for English editions), number of images, number of references (entries under a 参考文献 or References heading, plus footnotes), whether the site's brand line is mounted (an entry that links to the site's home page, usually the last reference), and whether the Center has the same work in the other language (known after an **Update**, for works the Center created in both languages). The last line is the agent and model that wrote the work, for example "Codex · 6.1 Terra" (one name per model, without its reasoning level, however the record wrote it), read once per version from the private writing record the Center keeps with each edition and kept on this device; "Writer not recorded" means the Center has none. Beside it is the machine that saved the work's first version, by the name its device was registered with in the Center (from the same private-notes reply, `firstMachine`; a Center without it leaves the machine out, and it is asked again in the next session). Clicking a card replaces the work everywhere: it opens in the note tab the plug-in used last, every RSSD tab switches to it, and whichever tab was in front stays in front; ⌘-click (Ctrl-click) opens it in a new note tab and leaves the others alone. The open work's card carries **Preview**, **Cards**, **Outline** and **Details**, each with its tab's icon, plus **Save** when it is edited. The button beside the search box switches to one line per work, where the dot is the local state: green synced, orange edited, blue saving, red conflict, grey not updated from the Center yet. Each device remembers its own choice. On desktop the ribbon switches the left sidebar between **Files**, **Search** and **Works** (the sidebar's own tab icons are hidden), and the sidebar's top row holds only these two buttons, on the left, as icons, with the sidebar button on the right (Update's tooltip says when the space was last updated, and Save carries the number of edited works as a badge); on mobile they stay in a footer, which also shows when the space was last updated. The two buttons: **Update** gets the Center's latest versions, and **Save** sends the edited works in the language on screen to the Center as private drafts, one after another, using the same save as the one-work command. Nothing is published. Save shows the count (for example "Save 3") and is greyed out while nothing is edited, or on mobile. A refused work (for example a conflict) is marked red and the rest continue; a space that refuses saves or a lost connection stops the batch. Everything is read from the vault, so the list is instant and works offline; whether the Center has a newer version still comes from an update. Obsidian's file tree stays available as another tab.

## Output themes

The site's own style (**Default**) is drawn in the section's colours and fonts and signed with the site's name marks at the top and bottom. WeChat shows the title large in its own field above the body, so the body never opens with it as a heading: the site's header at the top ends with a small title plate instead: the title centred on a light panel with a thin border, in 13px regular type and the column's colours. It is quiet enough to keep when the article is pasted under WeChat's own title, so nothing needs deleting. The Article preview shows the platform's own title above it, as a reader sees it. Chapters open the site's own way, and bold terms and inline code are marked the site's own way: Today with Roman numerals over a double rule, 研究方法 with numbered step blocks, 学术之门 with a tab on a bar, 犀术智法 with 第一部分 in a ruled box, 犀术国学 with 卷一 and a trigram that changes by chapter, 智能学堂 with LESSON 01 and a bar that fills as the lessons go, 犀术 IME with F1-style keycaps, 小猪盖被 with a large pale numeral, 学术海 with NO.01 and a wave, and 小猪萌宠 with each column's own icon and the chapter's number over a bubble, with no words (a paw for 每日一猫, a bone for 每日一狗, a turtle for 异宠大全 or an egg where the icon set has none, a newspaper beside the numbered tag for 宠物资讯, a paw elsewhere and in the header and signature). Icons are Obsidian's own Lucide icons (`getIcon`), never emoji: each goes into the article as a small picture in the column's colour, turned into a PNG while copying, because pasted editors take pictures, not inline SVG. Sub-headings, quotes, pictures and spacing follow the theme that matches the layout the website gives the section, so a news section stays compact and a gallery airy (`articleDesign` in `src/wechat-designs.mjs`). Columns of one site whose layouts match would share that theme, so each column also has its own variation of it, which changes the mark before a sub-heading, the frame of a quote and the edge of a picture: Plain (the theme as it is), Panel (a bar, a tinted panel, a mounted picture), Ruled (a dot, a quote centred between rules, a picture on a coloured base line) or Soft (a diamond, a double line, round corners). The table in `src/column-variants.mjs` gives every column one, and no two columns of a site share both theme and variation.
